# Native cryptography dependency review — 2026-09-08

The application uses the native pure ML-DSA-65 APIs: Node 24.20.0/OpenSSL 3.5.7 and Python cryptography 50.0.1/OpenSSL 4.0.2 in the local qualification environment. Pin the Python cryptography version and record the actual backend on every supported platform. Runtime support and interoperable signatures are evidence of compatibility, not module certification.

Reviewed the [NIST FIPS 204 potential-updates sheet](https://csrc.nist.gov/files/pubs/fips/204/final/docs/fips-204-potential-updates.xlsx), updated July 31, 2026. Its twelve entries clarify mathematical exposition, message notation, encoding order, bounds, links and signing rejection-loop estimates. Vella implements none of the underlying lattice arithmetic, NTT, Montgomery reduction or native rejection sampler; those remain native-provider responsibilities. Vella passes the full typed message to the pure signature API with empty native context, so the internal-message notation correction does not change its public envelope.

The sheet raises a suggested minimum allowed native signing-loop cutoff to 821. Inspected the corresponding [OpenSSL 3.5.7 signing source](https://github.com/openssl/openssl/blob/openssl-3.5.7/crypto/ml_dsa/ml_dsa_sign.c) and [4.0.2 source](https://github.com/openssl/openssl/blob/openssl-4.0.2/crypto/ml_dsa/ml_dsa_sign.c): their native signing loops have no fixed 814-iteration cutoff. Inference: that particular correction does not require changing Vella's application contract or a local iteration setting. This source check is not an exhaustive audit of the linked native binaries or all errata implementations.

The [OpenSSL pure-signature design](https://github.com/openssl/openssl/blob/master/doc/designs/ml-dsa.md) distinguishes native pure message encoding from prehash mode. The reference selects the pure API, performs no manual internal mu prehash, and exposes no caller-selected native message-encoding/context switch. Both runtimes produce independently verified vectors, with altered profile, payload, signature and key inputs rejected.

No FIPS-validation, external specialist certification or seven-year cryptographic lifetime claim follows. Annual security review must revisit provider advisories, NIST corrections and supported runtime versions. New provider/runtime versions require interoperability and workload requalification; do not silently downgrade when a required provider is unavailable.
